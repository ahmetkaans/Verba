## Rules

1. **Ask first.** Before changing any file (code, notes, documents, rules, tools), ask the owner about every important decision and wait for the answers. An answer covers only the item it was given for: a question, a request to explain, or a "yes" to one item is not a go-ahead for the other items. When unsure whether something was approved, ask.
2. **Plain files, no build step.** The game is plain files in `game/`: `index.html`, `css/`, `js/`, `data/` and `audio/`. No build step, no tools that must run before the game opens, no image files and no audio files except the word recordings in `game/audio/` (owner, 2026-11-22: one .mp3 per tested word, named after the word, made once by the private tool `.gitignore/audio/tools/make_audio.ps1` and shipped with a `LICENSE` file; the game only plays them, nothing has to run before it opens). It must open by double-click from the folder, offline. The only external resource is the Inter font from Google Fonts. File names are lowercase. Private material lives only in `.gitignore/`.
3. **Placeholder content.** Any text the owner has not explicitly named stays lorem ipsum. The list of names fixed by the owner is in docs/DESIGN.md.
4. **Don't decide open questions.** Do not invent rules for things that are still undecided (for example, the spelling rule for very short answers or the grammar content method). Follow the notes in README.md ("Open questions" and the Roadmap's open questions) and ask the owner.
5. **Numbers live in `CONFIG`.** Change times, points, thresholds and similar values only in the `CONFIG` object, and update the Configuration table in README.md whenever `CONFIG` changes.
6. **Test before handing over:**
   - no errors in the browser console;
   - works at phone width;
   - check both light and dark mode;
   - works with "reduce motion" turned on;
   - test remembered settings (language, theme, sound, same duration, SmartBoard mode, which questions the cards show) in a normal browser, because previews served as `data:` URLs block `localStorage`;
   - works both as a website and by double-click from the folder, offline (README.md, "Testing", "Website check").
   - the version numbers on the page's file links are current: after you change any file in `game/`, run `powershell -ExecutionPolicy Bypass -File .gitignore/tools/set_versions.ps1`, and `set_versions.ps1 -Check` must say OK before you commit (README.md, Roadmap item 11 and "Website check").
7. **Git.** Commit only when asked, with a meaningful message. Do not push unless asked. **Every commit adds an entry to `CHANGELOG.md`** (see README.md, "Changelog").
8. **Private `.gitignore/` folder.** The files in the `.gitignore/` folder must never be uploaded to GitHub: never `git add`, commit or push them. The folder is excluded locally through `.git/info/exclude` (a folder named `.gitignore` cannot work as an ignore file). It has six drawers: `tools/` (check scripts, test server, play-through test; `questions/` = question-writing helpers, `lib/` = helper library), `audio/` (`tools/` the old-Piper tools, `recordings/` the recordings workspace, `voices/` the Amy voice, `piper15/` the new Piper and its scripts, `third_party/` programs and docs that are not ours, `licence_evidence/`), `drafts/` (drafts in progress, sorted in `themes/`, `proposals/`, `mockups/`, `old/`), `words/` (word lists), `plans/` (theme plans in `questions/`, audio guide and log in `audio/`) and `archive/` (the old single-file version of the game, kept just in case: never changed, never needed for a task). For A1 work, read `words/ORG_A1_WORDS.md`. `words/A1_WORDS.md` should be read only when you work on creating a file in the same format as `ORG_A1_WORDS.md` (for example for another level), just to understand how the original word file is turned into a useful file for AI, or when the owner asks you to.
9. **Draft, validate, review, then write.** Don't add questions (or explanations, glossary meanings or target-word plans) to the files right after you write them. Write the draft in a draft file in `.gitignore/drafts/`, run the check script on it (README.md, "Check script") and fix what it reports. Show the owner a readable draft and remind the owner to ask you to review it against the "Review checklist" in README.md. The review is done by reading, item by item, with a quote as evidence for every hard item; a script result is evidence, never approval. Change the files only after that review and the owner's go-ahead. The steps are in README.md, "Workflow: draft → review → write".
10. **Check for inconsistencies first.** Check only the files you have read. If two of them disagree, quote both lines, tell the owner, and wait (owner's wording, 2026-11-19). Before doing anything the owner asks, check whether something stands in its way or doesn't fit together in what you have read: two rules that contradict each other, a rule that contradicts the request, docs that don't match the code (or the code and `CONFIG`), or anything else that is inconsistent (for example a target-word plan and its questions, or docs/DESIGN.md and the page). If you find something, tell the owner what it is and where, suggest a fix, and wait for the answer before you continue.
11. **Change a rule everywhere.** When you change a rule, a decision, a name, a number or any other fact, find every place it appears and change it in all of them: AGENTS.md, README.md (including its file map), docs/DESIGN.md, the game files (`game/index.html`, the css files in `game/css/`, the code in `game/js/` and the data in `game/data/`: code, `CONFIG`, comments, texts, styles, questions), the check script, the private files in `.gitignore/` (organized word files, plans; never `A1_WORDS.md` or another original word list, which are never changed) and your memory notes. Search for it (for example with grep) instead of relying on memory, because some rules are written in several sections of README.md. Then tell the owner which places you changed.
12. **Keep the file map true.** The "File map" in README.md must always match the files. In the same change, update it whenever you add, remove, rename or move a section banner, function, HTML id, data file, code file, CSS section anchor, doc heading or file that the map lists, or change what it says lives where. Then run `powershell -ExecutionPolicy Bypass -File .gitignore/tools/check_filemap.ps1`; it must say OK before you hand over. If the map and the files disagree, fix the one that is wrong and tell the owner (rule 10).
13. **Keep the question check script and its guide true.** When you add, change or remove a check, an option, a number or a file format the script depends on, update in the same change: the script's header, the guide in README.md ("Check script"), the list the script prints with `-Checks`, the self-test cases, and every place that quotes the expected result. Run the self-tests and compare the real bank's report before and after: it must stay the same unless the change is meant to change it, and then tell the owner what changed. Never weaken a check to make a question pass.
14. **Audio (the word recordings).** The recordings are made with the private tools in `.gitignore/audio/tools/` (the old Piper) and `.gitignore/audio/piper15/` (the new Piper), and the recordings workspace is `.gitignore/audio/recordings/`; the one guide is `.gitignore/plans/audio/AUDIO_GUIDE.md` and the list of every pronunciation problem is `.gitignore/plans/audio/audio_pronunciation_log.md`. Before any audio work (making, listening, fixing, copying, deleting) read both. The rules (owner, 2026-11-22, after a mistake that regenerated approved files): (a) **an approved recording is never regenerated** (Piper is random: the same word made twice sounds different; to change a word, make numbered takes in `_candidates`, the owner chooses, and the chosen take is copied); (b) **a theme is made only into its folder in `A1_VOICES/`** (`make_audio.ps1 -Theme N`, which refuses to write into `game/audio/`) and only `publish_audio.ps1` copies approved files to `game/audio/`; (c) **one word, one file, kept in every theme that needs it**: a word with one pronunciation has one recording and the same file (an identical copy) is kept in the folder of every theme that tests the word (`make_audio.ps1` copies it instead of making it again, `publish_audio.ps1` stops on two different takes in the theme folders); and **publishing never overwrites silently**: when a file already exists in `game/audio/` with a different take, `publish_audio.ps1` says so and the owner decides its fate (keep, replace with `-Replace`, or it is another pronunciation of the word); (d) **a word with more than one pronunciation uses the pronunciation of the meaning used in the theme**; this needs a naming rule, glossary links, tool support and a game change that are not built, so ask the owner when such a word appears; (e) **learn from the log**: before making audio use the log and the risk scan (`make_audio.ps1` prints both at its start), and after the owner listens add every new mispronunciation to the log and to `audio_fixes.txt`; when a pattern goes wrong a second time make it a sound rule (`$PHONEME_RULES`) or a scan pattern (`audio_scan.ps1`). Changing an audio tool or file name rule means updating the guide, the tool's header and the README "Word audio" section together (rule 11).
