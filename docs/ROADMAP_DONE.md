20. **Quit plays also when a tab or the browser is closed** (owner's idea and decision, 2026-11-13; **built 2026-11-13, in four steps**; see the "Quit plays" bullet in "History" for how it works now). This **replaces the earlier decision (2026-11-07) that only a reload is tracked.** **Idea:** when a real quiz starts, the game saves a small note with the game's identity; when the student leaves the quiz screen (finishes, quits, goes elsewhere) the note is removed; at **every** start-up the game looks for leftover notes and adds a "Quit" row to the History for each. No continuous writing: the note is written once per question, as the game already does. **What exists today:** the note (`saveQuizRun()`, `clearQuizRun()` in `js/history.js`, called from `renderQuestion()` and `showScreen()`) is kept in `sessionStorage`, which the browser clears when the tab closes, and `recordInterruptedQuiz()` reads it only after a reload (`wasReloaded()`). **The design (corrected after a review, 2026-11-13):** (1) every game gets an identity when it starts (`state.quiz.playId`), used by its note, by its quit row and by its finished record (`buildPlayRecord()` uses it instead of making a new id at the end); (2) **each game has its own note** in `localStorage`, named with that identity, because one shared note would be deleted by any other open tab that shows a menu, and two tabs playing at once would overwrite each other; a tab remembers only the name of its own note and removes only that one (`clearQuizRun()`); (3) **no tab names:** a page that has just started has no game running, so every leftover note it finds belongs to a dead game, or to a game in another tab that cannot be told apart from a dead one; both are recorded as a quit; (4) a quit row with the same identity is updated, never added twice; when a game finishes (`recordPlay()`), its finished record **replaces** a quit row with the same identity, so a mistaken quit from a tab that was still playing corrects itself; a note whose game is already in the history as a finished play is dropped; (5) the quit row says which question the student reached and the time that question started, and is put in the list by that time (not always on top); (6) a note is removed from the storage only after its quit row is saved, or when it is invalid; a blocked or full storage means nothing is tracked, as today. **Texts to change (shown to the owner first):** the "How your history works" note "Only reloads are noticed: if you close the tab or the browser during a quiz, nothing is saved." (`historyHowReloads`, English and Turkish; docs/DESIGN.md "History panel"). **Also update:** README "History" (the Limits and Quit plays bullets, the decided-for-the-next-steps bullet, Roadmap item 3), the comments in `js/history.js`, the file map, and the play-through tests (a note left by another tab becomes a quit row; a reload is not doubled; a finished game replaces its false quit; no duplicates; the row is put by its time; a blocked storage). **Steps:** 1. the code; 2. the tests; 3. the panel text; 4. the docs.

Saved at the owner's request as a reminder. **Before building the parts that are not built yet, ask the questions that are still open (see the end of this section), one by one,** (AGENTS.md rules 1, 4 and 9; the texts of comments and recommendations are drafted for review first). The build order agreed in principle: history, then the overall calculation and its comment, then the two reset buttons, then recommendations (last). Plan the shared data design together first, then build part by part.

**Wording.** *Play calculation* = the score on one results screen. *Overall calculation* = the long-term picture across all plays. Use these two terms from now on.

**1. History (owner's idea).** One record per finished play, saved in the browser (`localStorage`, not in the HTML file), shown like a browser history (a list, newest first, tap a record for details). A record holds the numbers of the results screen: date and time, level, category, topic, question type, difficulty, final score, counts of correct / partly correct / wrong / skipped answers, extra time used, whether same duration was on. Suggestion to confirm: also store whether SmartBoard mode was on (typed and tapped Fill are different tests). A record is about 250 bytes; the cap on the number of records goes in `CONFIG`.

**2. Export and import (owner's idea).** Easy to export (a small `.json` download) and import. The file carries a check number so the game can tell it is its own file: **1881** (the owner first said 1981 and corrected it), kept in `CONFIG`, together with the game name and a version. Honest note: it only catches wrong files by mistake; it is not protection, because anyone can read it in the page source.

**3. Overall calculation (owner's idea).** It considers the numbers of all plays together with their thematic or topical content and produces a comment that fits the situation. Not very complicated, but not so simple that it looks redundant; the comments should vary greatly across different combinations of numbers and plays (several variants, a rule against repeating the same one). Suggested design: store it separately from history as running totals per level, category, topic, question type and difficulty (number of plays, sum of scores), so each reset button works cleanly and capping history never changes it. The comment texts are drafted for the owner to review first (rule 3: lorem until named).

**4. Reset buttons (the owner left the method to me; names approved 2026-11-07).** Two buttons, **"Clear history"** (clears the list, keeps the overall calculation) and **"Reset calculation"** (clears the totals, keeps the history), each with an "are you sure" pop-up that says what it deletes and what it keeps (same style as the Main menu pop-up).

**5. Recommendations (owner's idea).** A general recommendation covering every play so far, shown only after at least **7** plays (the number goes in `CONFIG`); before that, a message such as "You need to play at least 7 games to see a general recommendation" (where it is shown and the wording are not decided). The general screen is accompanied by game-specific recommendations; what they say and what triggers them are not decided.

**Things to settle before building (rule 10).** Roadmap item 3 has the open question "latest try only or every try"; lorem (placeholder) quizzes have no real content, so suggest not recording them; the results page may note whether SmartBoard mode was on.
