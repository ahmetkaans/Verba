## What to read (and what not)
- **Writing, checking or reviewing questions or glossary meanings:** read `docs/ADDING_QUESTIONS.md` and nothing else first. It lists the few README sections you need. For **new question work at any level** (A2 to C1, new A1 work such as grammar) also read `docs/QUESTION_METHOD.md` (the level rule, level settings and the step order; it wins over the recipe where they differ, and a disagreement goes to the owner, rule 10).
- **Changing the game (code, css, data, a text, a number):** README "File map", **section A only**, to find your task's row; then read the README / DESIGN sections it points to. To print one section without opening the whole file: `python -I .gitignore/tools/show_section.py "<heading>"` (`--file docs/DESIGN.md` for DESIGN; `--list` lists the headings with their line number and size; `--find <word>` shows which headings and sections use a word). To edit a section: take its line from `--list`, `Read` that range with `offset`/`limit`, then `Edit`; never read a whole README or DESIGN. Before a change, also read README "Confirmed decisions" and the matching "Change together" row of the map (rows B to E, same tool).
- **A plain question about how things work:** you may skip "Confirmed decisions" and "Change together". When unsure, read more, not less.
- **Making, listening to, fixing, copying or deleting word recordings (audio):** read `.gitignore/plans/audio/AUDIO_GUIDE.md` completely first, then `.gitignore/plans/audio/audio_pronunciation_log.md` (rule 14). Nothing else is needed for audio.
- **Never read** (large, generated or old): a whole theme file or `game/data/glossary/a1.js` (search them: `.gitignore/tools/bank_index.py --word <word>`), `.gitignore/archive/`, `.gitignore/drafts/**/*_ALL.json`, `.gitignore/tools/playthrough.js`, the `.mp3` and `.wav` files of `.gitignore/audio/` (its `.md` notes are fine to read), `.gitignore/audio/third_party/piper_old/`, `.gitignore/audio/voices/` and `.gitignore/audio/piper15/venv/`. Of `.gitignore/audio/third_party/` read only a named file (the trimmed docs are small). `CHANGELOG.md`: do not read it; add an entry with `changelog_add.py` (see Commands).
- **Reports and sheets:** the tools write their full reports to disk. Read them from disk with `offset`/`limit` or print only the short view; never print a whole report, blueprint or review sheet in chat.
- Edit README.md and docs/DESIGN.md when it is needed and logical: README holds the algorithms and details a future change needs, DESIGN the design process and language.

## Rules (full text: `docs/RULES_FULL.md`, same numbers)
1. **Ask first.** Before changing any file, ask the owner about every important decision and wait. An answer covers only its own item; a question, an explain request or one "yes" is not a go-ahead for the rest. The one exception is the small fixes of rule 17.
2. **Plain files, no build step.** `game/` = `index.html`, `css/`, `js/`, `data/` and `audio/` (the word recordings, one .mp3 per word, made by `.gitignore/audio/tools/make_audio.ps1`, with a licence file; owner, 2026-11-22); opens by double-click, offline; no other audio and no image files; only the Inter font is external; lowercase file names; private material only in `.gitignore/`.
3. **Placeholder content.** Text the owner has not named stays lorem ipsum (names fixed by the owner: docs/DESIGN.md).
4. **Don't decide open questions.** Follow README "Open questions" and the Roadmap's, and ask.
5. **Numbers live in `CONFIG`.** Change them only there, and update the README Configuration table.
6. **Test before handing over:** no console errors; phone width; light and dark; "reduce motion"; remembered settings (in a normal browser, not a `data:` preview); website and double-click offline (README "Testing", "Website check"); after any change in `game/` run `python -I .gitignore/tools/set_versions.py`, and with `--check` it must say OK before you commit.
7. **Git.** Commit only when asked, with a meaningful message; don't push unless asked; **every commit adds a `CHANGELOG.md` entry** (README "Changelog").
8. **Private `.gitignore/` folder.** Never `git add`, commit or push it (it is excluded through `.git/info/exclude`). Drawers: `tools/` (the daily tools; `questions/` = question-writing helpers, `lib/` = helper library), `audio/` (`tools/` the old-Piper tools, `recordings/` the recordings workspace, `voices/` the Amy voice, `piper15/` the new Piper and its scripts, `third_party/` programs and docs that are not ours, `licence_evidence/`), `drafts/`, `words/`, `plans/` (`questions/`, `audio/`), `archive/` (never changed, never needed). For A1 read `words/ORG_A1_WORDS.md`; `words/A1_WORDS.md` only to build a file in the same format or when asked.
9. **Draft, validate, review, then write** (README "Workflow: draft → review → write"): drafts only in `.gitignore/drafts/`, run the check script, show a readable draft, review item by item with a quote as evidence (a script result is evidence, never approval), change the files only after the owner's go-ahead.
10. **Check for inconsistencies first.** Check only the files you have read. If two of them disagree (rules that contradict, docs vs code vs `CONFIG`, a plan vs its questions), quote both lines, tell the owner, suggest a fix, and wait. **Root cause first:** when a script fails, a check catches an error or a step costs extra effort, find the cause before patching, then propose a backward-compatible guard for the whole class of error (a new check plus a self-test, a tightened rule, a structural guard); never weaken a check, cap or CEFR ceiling to pass; wait for the owner. **Spotted while working:** while reading files the task already needs (no extra reads), note any stale path or doc, inconsistency or clear token or speed gain in a short "Spotted while working" note at handoff; touch nothing outside the task until the owner approves.
11. **Change a rule everywhere.** Search (grep) for every place a rule, name, number or fact appears: AGENTS.md, `docs/RULES_FULL.md`, `docs/ADDING_QUESTIONS.md`, README (including its file map), docs/DESIGN.md, the game files, the check scripts, the private files (never `A1_WORDS.md` or another original word list) and memory notes. Tell the owner which places changed.
12. **Keep the file map true.** Update README "File map" in the same change when anything it lists is added, removed, renamed or moved, then run `powershell -ExecutionPolicy Bypass -File .gitignore/tools/check_filemap.ps1`; it must say OK.
13. **Keep the question check script and its guide true.** When a check, option, number or file format changes, update the script's header, the README "Check script" guide, the `-Checks` list, the self-tests and every quoted result; compare the real bank's report before and after; never weaken a check to make a question pass.
14. **Audio (the word recordings).** Read `.gitignore/plans/audio/AUDIO_GUIDE.md` and `audio_pronunciation_log.md` before any audio work. Never regenerate an approved recording (Piper is random: a remake is a different take). Make a theme only into its folder in `.gitignore/audio/recordings/A1_VOICES/` (`make_audio.ps1 -Theme N`, never into `game/audio/`); only `publish_audio.ps1` copies approved files to `game/audio/`. One word has one file, and the same file is kept in the folder of every theme that needs it; `publish_audio.ps1` never overwrites an existing different file silently (it says it already exists and the owner decides); a word with several pronunciations uses the one of the theme's meaning (not built: ask the owner first). Log every new mispronunciation in the log and `audio_fixes.txt` and learn from the log for the next theme.
15. **Two hats, always.** Work as a software engineer (modular, fast, deterministic, regression-free scripts, code, data and files) and as an experienced EFL teacher (every word split, wrong option, collocation, hint and game mechanic is pedagogical, fair and clear for that CEFR level). Never sacrifice teaching quality for a quick code hack, and never write fragile or bloated code for a narrow teaching edge case; when they pull apart, say so and ask (owner, 2026-11-24; docs/QUESTION_METHOD.md, "Dual working principle").
16. **Four habits, in every folder (owner, 2026-11-24).** (a) **Tidy and modular:** `game/` is production only, `docs/` documentation, `.gitignore/` private: `tools/` (`questions/` helpers, `lib/`), `plans/`, `words/`, `drafts/` (`themes/` active drafts only, `gen/` generator scripts, `proposals/`, `mockups/`, `old/`), `audio/`, `archive/` (history, never changed); no temp files or `__pycache__` in the tree; flag stale drafts, duplicate or retired scripts and misplaced files, and move or delete them only with the owner's approval; a script is retired only after its replacement passes a byte-for-byte or golden-output test. (b) **Codify every lesson in the right permanent file, starting from the root cause (rule 10)** (full table in `docs/RULES_FULL.md` rule 16): method and pedagogy in `docs/QUESTION_METHOD.md`, word limits in `plans/questions/*.txt`, a recurring error as a new check plus a self-test (rule 13), a rule here and in RULES_FULL (rule 11). Memory keeps the owner's preferences plus ONE rolling state note (`project-a2-themes-progress`). (c) **Keep wiring in sync by automated check, not memory:** theme registration (`js/topics.js`), data files and script tags, glossary, audio files, bank index, file map, versions. (d) **Optimize safely:** small backward-compatible changes, never weaken a pedagogical check, a repetition cap or a CEFR ceiling, and after any script or code change run `python -I .gitignore/tools/run_all_tests.py` (the whole regression suite; list in RULES_FULL rule 16) and report 0 regressions. (c) is checked by `sync_check.py`.
17. **Fix small things quietly, ask about big ones (owner, 2026-11-25).** As coder and EFL teacher, fix small coding, formatting, wrong-option, sentence and rule-edge problems yourself with your best pedagogical and logical judgment, and list every such fix in a short table at the end of the turn (row, before, after, why). **Always ask first, in plain words,** before changing: core game logic, code architecture or engines; a word's core meaning or tested type; an approved plan (the split, the test counts); a level-share exception; the repetition cap; or any check (never weaken one; rules 10 and 13). Full text: `docs/RULES_FULL.md`.
18. **Circuit breaker (owner, 2026-11-25).** Stop at once when an action drags (a command over about 2 minutes), loops (three fix rounds on one question type) or hits the same error twice on the same row or file. If the cause is small, fix it and say so in the summary; if it needs anything from the list in rule 17, stop and ask in plain words. Full text: `docs/RULES_FULL.md`.
19. **Clean-desk flush (owner, 2026-11-25).** Extends rule 16(b): before the final reply of any finished task, save its new lessons, open items and state in their permanent file (a memory note or a plan file without asking; rule files, `docs/QUESTION_METHOD.md` and game files only as rule 1 and 17 allow; `CHANGELOG.md` only with a commit, rule 7), then end the reply with a 3-line status block: `Saved to disk`, `Uncommitted / open`, `Next step`. Overwrite the state note, never append. A dated or finished note is retired in the same flush. `MEMORY.md` stays at or below ~30 lines and 4 KB (each line ≤ 150 chars). Full text: `docs/RULES_FULL.md`.

## Commands
- Question check: `python -I .gitignore/tools/questions/check_brief.py --only 'A1|vocabulary|4|'` is the **short view** to use in chat (same arguments and exit code as `check_questions.py`; it prints the summary, every error, warnings counted per check, and what is new; the full report goes to `%TEMP%\check_brief_full.txt`). The bare `python -I .gitignore/tools/check_questions.py [--only ...]` gives the full report (about 1 second; no option checks the whole bank, about 180 lines; options: README "Check script"; the old `check_questions.ps1` is frozen as the oracle in `.gitignore/archive/tools/ps_oracles/`). Self-tests: `python -I .gitignore/tools/test_check_questions.py`.
- Changelog entry (rule 7, no need to read the file): `python -I .gitignore/tools/changelog_add.py --title "Short title (documentation only)" --body "Two or three plain sentences."` (`--date YYYY-MM-DD`, `--dry-run`); it puts the entry under the newest date, or makes a new date heading. The commit ID is added by hand after the commit.
- Bank index (counts, line of each quiz, where a word is used): `.gitignore/tools/bank_index.py`.
- File map: `.gitignore/tools/check_filemap.ps1`. Versions: `python -I .gitignore/tools/set_versions.py --check`.
- Draft of a new theme (2026-11-24): `python -I .gitignore/tools/questions/pool_check.py --level A2 --theme "<name>"` before the plan is approved, `python -I .gitignore/tools/questions/draft_check.py --prefix <Prefix>` for the whole draft check, `risk_table.py --prefix <Prefix>` for where a second answer is likely (docs/QUESTION_METHOD.md, "The tools").
- Audio (read `AUDIO_GUIDE.md` first): `.gitignore/audio/tools/make_audio.ps1 -Theme N -NoPlay` (into the theme folder), `.gitignore/audio/tools/audio_scan.ps1 -Theme N` (risky words), `.gitignore/audio/tools/publish_audio.ps1 -DryRun` (copy the approved files to the game).
